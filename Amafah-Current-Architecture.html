AMAFAH PURCHASE MANAGER · SIMPLE GUIDE

How a supplier’s message
becomes a quote and a reply

7 November 2026 · Based on the current local project files

What this guide shows: how the code works today. Some local changes have not been confirmed on the running app. The security improvements we discussed are not finished yet.

1. The main idea

Supplier sends a message → OpenClaw receives it → AI reads it → AI asks tools for help → the purchase app checks and saves details → OpenClaw sends the reply.

The AI understands the conversation and writes replies. The purchase app holds the records and checks what is allowed. OpenClaw connects the AI to WhatsApp.

4. Example: one supplier sends one price

Supplier: “The LED light is AED 25 each. Delivery in 3 days.”

  1. Receive: OpenClaw sees the message and the sender’s WhatsApp details.
  2. Check whether to respond: The app checks whether this is our supplier, whether there is a buying request to discuss, and whether automatic replies are allowed.
  3. Find the product request: AI reads the current buying requests. If the supplier replied directly to an earlier request, that helps identify it. If the meaning is unclear, AI should ask one short question.
  4. Save the quote: A tool asks the purchase app to save AED 25 and the delivery details against the chosen supplier and request. The app checks ownership and whether the request is still open.
  5. Choose the next step: AI may acknowledge the quote, ask a question or propose negotiating. For an offer or acceptance, it is instructed to use the commercial-check tool first.
  6. Check permission: The app checks the proposed terms against buyer limits. If the proposal is wrong, it returns feedback. If it still cannot be corrected after two proposal attempts, the AI is told to ask a person for help.
  7. Reply: AI writes the message. OpenClaw applies its sending checks and sends it through WhatsApp.
  8. Save the result: The app records whether sending succeeded. Writing a reply and successfully sending it are separate events.

If the supplier lists several products: a combined tool can read and save all their quotes together. If any line is unclear, it keeps the known details while asking for clarification.

6. What happens when something is wrong?

ProblemWhat the code does nowWhat that means
Supplier or buying request belongs to another businessThe purchase app rejects the protected operation.The AI cannot simply choose any record and change it.
More than one buying request might matchReturns possible matches; instructions tell AI to ask a focused question and keep known facts.Being on the supplier’s request list does not prove that the product match is correct.
Offer goes beyond buyer limitsThe commercial checker rejects it or asks for a correction or human help.The AI chooses wording and strategy, but it does not get unlimited permission to buy.
Acceptance has no valid approvalThe acceptance tool rejects the operation.A saved deal needs a matching approval for that exact quotation.
Automatic reply was deniedThe sending check blocks tracked denied replies in direct supplier chats.The code has a real block for these cases, not only an instruction to the AI.
Supplier identity cannot be readThe AI receives a warning.This path is weaker than an explicit block and needs improvement.
Outgoing reply has no matching saved messageRecords a warning but still allows sending.We cannot yet say every sent reply is linked to the correct saved buying request.
AI changes the price in its final wordingThe final sending step does not require a matching commercial approval.A successful earlier check does not prove the exact WhatsApp text is correct. This is an important gap.

7. What the AI can decide, and what the app checks

AI handles the conversation

  • Understand what the supplier means.
  • Work out which product they are discussing.
  • Choose a negotiation approach.
  • Ask a short clarification question.
  • Write a natural reply.

The app checks records and permission

  • Does the supplier belong to this business?
  • Is the supplier linked to this buying request?
  • Is the request still open?
  • Are the proposed terms within buyer limits?
  • Is there valid approval to accept this quote?

Some steps still depend on AI following its instructions. They are not all forced by code.

8. Where extra AI work and tokens come from

A short supplier message can require much more information than its own words. The AI may also read rules, earlier messages, tool descriptions and buying details.

After a tool answers, the AI may think again and call another tool. Some tools also ask the model to do a separate reading task, such as extracting several prices or comparing quotes. Those extra tasks add usage.

One supplier message can therefore use several AI calls. We have not measured an exact total for a real message yet. Use /usage tokens, /status and /context detail in the relevant OpenClaw chat to inspect the reported usage.

9. Other ways messages start

  • Buyer starts a request: the dashboard asks the app to send product requests to suppliers.
  • Reminder becomes due: the app can ask AI whether a reminder is still useful. It should avoid reminding a supplier who has already answered.
  • Buyer gives an instruction: the app passes that instruction into the supplier’s conversation.
  • Quotes need comparing: the app can ask AI to rank saved offers. A recommendation is not permission to accept an order.

These app-started messages use separate paths. We should not assume they pass through exactly the same checks as a reply to an incoming supplier message.

10. Where these parts live

amafah-purchase-manager-ai-agent contains the purchase app. Its main files are main.py for buyer requests and reminders, openclaw_bridge.py for the AI’s business actions, auth.py for buyer sign-in checks, and db.py for saved records.

The separate OpenClaw repository currently sits inside it at openclaw-railway-template. Its src/server.js starts and watches OpenClaw. Its plugins/procurement-tools/dist/index.js defines the 17 tools and the message checks.

Local versus live: both repositories have unfinished, uncommitted changes. Some move older Groq-based AI work into OpenClaw. We have not confirmed that these changes, the selected model, or every security check are active on Railway.

Our intended improvement: give AI a short, useful set of buying details; let it speak naturally; enforce the correct supplier, buying request, recipient and allowed action in code. That improvement is a plan, not a completed feature.

This document explains the current code. Creating it did not send messages, change purchase records or deploy the app.
